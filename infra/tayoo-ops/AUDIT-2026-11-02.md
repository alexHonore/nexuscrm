# Audit post-migration — Groupe Nexus CRM sur Tayoo Ops (2026-11-02)

Audit fait juste après la bascule (production = `https://web-nexuscrm.tayoo.app`,
instance `nexuscrm` du VPS `31.97.147.222`). Lecture seule, sauf les corrections
listées au §1, faites le même jour avec l'accord de l'exploitant.

- §1 : corrigé le 2026-11-02 (et comment revenir en arrière).
- §2 : **à revoir** — classé par priorité, rien n'y a été touché.
- §3 : vérifié et sain.

## 1. Corrigé le 2026-11-02

### H-3 · SSH : mots de passe refusés depuis Internet

- `/etc/ssh/sshd_config.d/00-tayoo-hardening.conf` : `PasswordAuthentication no`,
  `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`,
  `MaxAuthTries 4`, `LoginGraceTime 30`. Lu avant `50-cloud-init.conf`
  (première valeur lue = celle qui gagne).
- Exception en fin de `/etc/ssh/sshd_config` : `Match Address 127.0.0.0/8,::1,172.16.0.0/12`
  → mot de passe et root permis **seulement** depuis la machine et les réseaux
  Docker. Raison : le nœud « Habitam sign-in » de n8n (credential « SSH Password
  account ») se connecte en root **par mot de passe** depuis `172.19.0.0/16`
  (aide `/root/.local/share/habitam`). Sans cette exception, les leads Habitam
  s'arrêtaient.
- fail2ban installé, prison `sshd` (`/etc/fail2ban/jail.d/tayoo-sshd.local`) :
  5 échecs en 10 min = 1 h de bannissement ; réseaux locaux jamais bannis.
- Vérifié : nouvelle connexion par clé OK ; depuis Internet seul `publickey` est proposé.
- Revenir en arrière : `sshd_config.bak-20261102T015212Z`, supprimer le fichier
  `00-tayoo-hardening.conf`, `systemctl reload ssh`.
- **Suite** : passer le credential n8n Habitam à une clé SSH, puis retirer le bloc `Match`.

### M-10 · Kamailio : port 5066 (WebSocket en clair) fermé à Internet

- Unité `tayoo-guard-5066.service` (persistante) : règle iptables
  `INPUT -p tcp --dport 5066 ! -i lo ! -s 172.16.0.0/12 -j DROP`.
  Seul le pont TLS `nexus-ws-bridge` (réseau Docker `root_web`) y parle.
  Aucun fichier de la passerelle vocale modifié.
- Vérifié : depuis Internet le port ne répond plus ; `wss://srv892958.hstgr.cloud/ws`
  répond toujours 101 ; la session du pont vers Kamailio est restée ouverte.
- Revenir en arrière : `systemctl disable --now tayoo-guard-5066`.

### M-5 · Base du VPS : plus rien de lisible par l'API Data

```sql
REVOKE ALL ON ALL TABLES    IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;
REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA public FROM PUBLIC, anon, authenticated;
-- + ALTER DEFAULT PRIVILEGES … REVOKE … pour les rôles postgres et supabase_admin
```

Avant : `anon` et `authenticated` lisaient les 41 tables (34 sans RLS) ; seule la
case « privée » de l'instance les protégeait. Après : 0 / 41. L'app n'utilise
pas PostgREST : aucun effet sur elle.

### M-8 · L'app ne se connecte plus en `postgres`

- Rôle `nexuscrm_app` : `LOGIN BYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION`,
  `search_path = public, extensions`, droits SELECT/INSERT/UPDATE/DELETE sur les
  tables de `public`, USAGE/SELECT/UPDATE sur les séquences, EXECUTE sur les
  fonctions, + privilèges par défaut (rôles `postgres` et `supabase_admin`) pour
  les tables futures. `BYPASSRLS` : 7 tables ont RLS activé sans politique.
- Mot de passe : propre au rôle (plus celui de l'instance, que partagent tous les
  services Supabase), posé sous forme de **vérificateur SCRAM** — l'instance
  journalise les DDL (`log_statement = ddl`), un mot de passe en clair y aurait fini.
  Il n'existe que dans `app.env` (`DATABASE_URL`, `application_name=nexuscrm_app`).
- Vérifié : connexion TCP, lecture des 41 tables, app saine, 0 erreur de droits.
- Les migrations de schéma restent en `postgres` (portail / `sb apply`).
- Revenir en arrière : `app.env.bak-20261102T015610Z` (ancienne `DATABASE_URL`) puis
  `build-and-deploy.sh "$(cat image.ref)"`.
- Changer le mot de passe : générer un vérificateur SCRAM (même méthode),
  `ALTER ROLE nexuscrm_app PASSWORD '<vérificateur>'`, mettre à jour `app.env`, ré-héberger.

### M-7 · Limite de ~100 s de Cloudflare

- `DISPATCH_BUDGET_MS=80000` dans `app.env` (240 000 par défaut) : un cycle du
  dispatcher ne peut plus dépasser la coupure de Cloudflare (n8n le relance chaque minute).
- Mesuré sur l'historique n8n (Vercel) : dispatcher < 1 s, rappels ≈ 1 s,
  synchro CDR 18–34 s. Rien près de la limite aujourd'hui.
- **Reste** (§2, M-7b) : 18 routes autorisent 120–300 s.

### M-6 · En-têtes de sécurité

`next.config.ts` (les deux hébergements) : `Strict-Transport-Security`
(2 ans, que Vercel posait seul et qui manquait derrière Cloudflare),
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Content-Security-Policy: frame-ancestors 'none'`, `Referrer-Policy`,
`Permissions-Policy` (micro permis à l'app : téléphone web). Pas de CSP de
scripts (voir §2).

### M-9 · Ressources partagées

- Plafond CPU de l'instance `nexuscrm` : 1 → **2** (portail, opération `configure`).
  L'app reste plafonnée à 1 CPU par le portail ; la base profite du reste.
- `build-image.sh` refuse de construire pendant les heures d'appel
  (lun.–sam. 8 h–21 h, heure de Toronto) sauf `FORCE=1` : le build tourne sur le
  serveur de production, à côté de la base, de n8n et de la passerelle vocale.

### M-4 · Surveillance

Workflow n8n « NexusCRM — surveillance (Tayoo Ops) » (`uLPuyVOQU441FrCU`) :

1. toutes les 5 min, `GET https://web-nexuscrm.tayoo.app/login` (par Cloudflare) ;
   courriel à `info@alexhonore.com` après 2 échecs de suite, puis au retour ;
2. workflow d'erreur de « Groupe Nexus CRM — crons (Tayoo Ops) » : un courriel au
   plus par 30 min quand un cron échoue (couvre aussi une base en panne).

Envoi par le credential Gmail de `info@alexhonore.com`, **vers `info@`** :
`alex@alexhonore.com` est un alias de cette même boîte, et Gmail range un courriel
de `info@` vers son propre alias dans « Envoyés » seulement (essayé : libellé
`SENT` sans `INBOX`). Vers `info@` lui-même, il arrive dans la boîte de réception
(essayé : `INBOX`, `UNREAD`). Le second credential n8n « Gmail account » est
expiré, et son app OAuth est en mode test : Google y coupe l'accès tous les 7 jours.
Logique des deux branches testée (exécution simulée).

### H-2 · Ancienne base cloud : API Data désactivée

Fait par l'exploitant le 2026-11-02 (tableau de bord Supabase → Data API).
Vérifié de l'extérieur avec la clé publique : point d'entrée d'une table et
GraphQL répondent 503, aucune ligne lisible. Le conseiller signalera toujours
« RLS désactivé » (réglage de la base), mais sans API ce n'est plus exposé.

## 2. À revoir

### 🔴 Haute

**H-1 · Copie hors serveur — FAIT le 2026-11-02.** Seau R2 `tayoo-backups` (verrou 30 jours,
suppression à 35), copie chiffrée chaque nuit à 04:30 UTC, test de restauration mensuel —
voir `offsite/README.md`. Premier envoi : 23 sauvegardes (maa, nexuscrm, tayoo) ; test de
restauration OK pour les trois. **Reste à faire par l'exploitant : copier les 3 clés
`/srv/supabase/offsite/keys/*.key` hors du serveur** (sans elles, les copies sont illisibles).

**H-2b · Ancienne base cloud : RLS et droits `anon` toujours en place.** L'API
Data est coupée (§1), donc rien n'est exposé ; mais si quelqu'un la réactive,
les 34 tables sans RLS redeviennent lisibles avec la clé publique. Si l'on garde
ce projet au-delà de la période de repli, y appliquer les mêmes `REVOKE` qu'au
VPS (§1, M-5). Sinon, le mettre en pause à la fin du repli règle la question.

### 🟠 Moyenne (reliquats)

- **M-7b · Routes au-delà de 100 s.** `cron/transcripts`, `cron/sync-cdr`,
  `campaigns/[id]/enroll|enrollments|reopen`, `assistants/import`,
  `assistants/[id]/suite`, `admin/voipms/*` (commande / routage / annulation de
  DID, sous-comptes), `admin/calls/sync`, `admin/calls/[id]/recording` (300 s) ;
  `assistants/[id]/sandbox`, `admin/telephony-usage`, `admin/recordings*` (120 s).
  En auto-hébergé Node ignore `maxDuration` : le travail continue, mais
  l'utilisateur voit une erreur 524 de Cloudflare. Si cela arrive : répondre tout
  de suite (202) et finir dans `after()`. Surveiller la première exécution du cron
  `transcripts` (11 h 45 UTC).
- **M-9b · Audio des appels.** `rtpengine` n'a aucune priorité CPU sur le reste
  de l'hôte (charge observée 3,5 / 4). Envisager une priorité temps réel ou des
  CPU réservés pour la passerelle — chantier de la passerelle, non touché ici.
- **M-10b · Pare-feu global.** `ufw` est inactif. Un pare-feu complet (22, 80,
  443, UDP SIP/RTP de la passerelle) demande d'inventorier les ports de la
  passerelle vocale avant d'activer quoi que ce soit — risque de couper les appels.
- **M-4b · Sonde externe.** La surveillance tourne sur le même VPS : si le serveur
  entier tombe, aucun courriel ne part. Ajouter une sonde extérieure (UptimeRobot,
  Better Stack, Cloudflare Health Checks…).
- **M-4c · Portail.** La santé de l'app hébergée n'apparaît pas dans le badge
  « HEALTHY » du portail ni dans ses alertes (seuls les services `sb-*` comptent).

### 🟡 Basse

- **Secrets exposés à faire tourner** : les 3 mots de passe Studio (en-têtes
  `Authorization: Basic` du Caddyfile du routeur, affichés le 2026-11-01) ; la clé
  du webhook de leads (collée dans une conversation, et écrite en dur dans le
  nœud « Push CRM » de n8n — la passer dans un credential) ; les éléments du §10
  de la passation.
- **Identifiants de l'ancienne base sur le VPS** (`reverse-sync.env`) : à retirer
  à la fin de la période de repli (rappel programmé le 2026-11-23).
- **Abonnements push** : les 4 abonnements datent de l'ancien site (autres clés
  VAPID) ; les envois vers eux échoueront. Les téléphonistes réactivent les
  notifications sur la nouvelle adresse.
- **Ménage** : 3,5 Go de cache de build (`docker builder prune`) ; plusieurs
  copies `app.env.bak-*` contenant des secrets (600, root) ; aucun nettoyage du
  registre d'images (`registry garbage-collect`).
- **Déploiement** : manuel, sans tests automatiques avant le build ; garder la
  liste des empreintes `@sha256` déployées (`image.ref` ne garde que la
  dernière) pour pouvoir ré-héberger la précédente.
- **Postgres** : réglages par défaut (`shared_buffers = 128MB`) — suffisant pour
  69 Mo de données, à revoir si la base grossit.
- **Conseiller Supabase** (même schéma au VPS) : `assistants_activation_gate`
  sans `search_path` fixé ; `rls_auto_enable` (SECURITY DEFINER, fonction de
  déclencheur d'événement, non appelable telle quelle — signalée tout de même).
- **CSP de scripts** : seule `frame-ancestors` est posée ; une CSP complète
  demanderait de recenser Twilio, JsSIP, Google et les scripts en ligne de Next.
- **Studio** : les pages Logs / Observability ne fonctionnent pas (la pile
  auto-hébergée tourne sans collecteur de journaux).

## 3. Vérifié et sain

- L'app n'est joignable que par le tunnel Cloudflare : `cf-connecting-ip` ne peut
  pas être falsifié (la vraie IP apparaît dans `/admin/audit`) ; Traefik ne la
  sert pas ; tous les ports de l'instance et de l'app écoutent sur 127.0.0.1.
- API Supabase de l'instance privée : 403 depuis Internet.
- Conteneur de l'app : uid 10001, système de fichiers en lecture seule, 1 Go,
  réseau isolé (le sien + celui de l'instance) ; aucun secret dans l'image.
- `app.env`, `reverse-sync.env`, `.website.env` : 600, root.
- Fichiers statiques mis en cache par Cloudflare (`immutable`, HIT).
- Ancien site en pause, copie inverse active (toutes les 15 min), retour arrière
  répété avec succès contre la vraie base cloud.
